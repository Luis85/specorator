# Tasks / Agent Board Feature

`features/tasks` owns Markdown work orders, Agent Board UI, task prompt rendering, run coordination, and generated ledger/handoff writes.

## Boundaries

- Task code may call chat only through `TaskExecutionSurface`.
- Direct chat must not depend on tasks.
- Provider-specific behavior stays behind `ChatRuntime`, `ProviderRegistry`, and existing chat controllers/renderers.
- Work-order notes are the durable source of task state for this feature slice.
- WO card right-click is a renderer→view callback seam (`AgentBoardRenderCallbacks.onContextMenu`) dispatched through `ui/workOrderContextMenu.ts`, which reuses `features/quickActions/` helpers without coupling tasks to chat.

## Run state — sidecar vs work-order note

To avoid racing the agent's `Edit` tool against the work-order checklist, run state is split across two surfaces:

| Surface | What lands | When |
|---|---|---|
| `.specorator/runs/<runId>/heartbeat.json` | `{ at, status, pauseReason? }` (`RunSidecarHeartbeat`) | every 30s heartbeat tick |
| `.specorator/runs/<runId>/ledger.jsonl` | one JSON-encoded `TaskLedgerEntry` per line | every ledger flush (per progress block, tool call, status transition) |
| Work-order note frontmatter | `status`, `run_id`, `heartbeat`, `started`, `attempts`, `pauseReason` | run start, pause, resume, terminal — turn boundaries only |
| Work-order note `<!-- specorator:run-ledger-* -->` region | full sidecar ledger rendered as `- <ts> [<status>] <message>` lines | once at terminal (after handoff write) |
| Work-order note `<!-- specorator:handoff-* -->` region | structured handoff markdown | once at terminal (review path) |

- **`ui/WorkOrderActivityProvider`**: plugin-level activity provider for the chat header dropdown. It indexes active `running` / `needs_input` / `needs_approval` work orders, exposes counts and rows through `core/types/workOrderActivity`, switches to live sidepanel tabs when possible, and falls back to a read-only-safe `WorkOrderDetailModal`.
- **`storage/RunSidecarStore`**: filesystem only. Owns heartbeat I/O, single/batch ledger append, deduping reads, snapshot, finalize-failure markers, run listing, and cleanup. Each appended entry gets a stable id before the serialized batch write; `readLedger` dedupes by id (legacy rows fall back to timestamp/status/message), skips malformed JSON lines, and tolerates CRLF. Snapshot flattens embedded newlines so one entry = one markdown line.
- **`storage/TaskNoteStore`**: `writeLedgerSnapshot(content, markdown)` mirrors `writeHandoff` — replaces the run-ledger region atomically. Throws on missing markers.
- **`execution/RunSession`**: heartbeat + `LedgerWriter` batches route directly to sidecar. Every terminal path awaits `LedgerWriter.finalize()` through retry/backoff drain before snapshotting; partial terminal batches can never be snapshotted ahead of their trailing entries. Snapshot/note failures still settle the run, but are recorded through the finalize-failure path.
- **`execution/TaskRunCoordinator`**: wires deps from view → session. `appendLedger` closure injects `task`; `writeHeartbeat`/`finalizeLedgerToNote` are direct method refs on the dep.
- **`ui/AgentBoardView`**: wires `plugin.runSidecarStore` into the coordinator. Owns three lifecycle hooks against the sidecar:
  - **GC on terminal**: `finalizeLedgerToNote` calls `cleanupRun(runId)` only after the snapshot lands. A failed note finalization writes `finalize-failed.json`; startup sweep preserves that sidecar for recovery instead of deleting the only durable ledger copy.
  - **Startup sweep**: `sweepStaleSidecars()` runs in `onOpen` after `refresh()` and before `recoverOrphanedRuns()`. Removes any `<runId>` dir not matched by a non-terminal task with that `run_id`.
  - **Periodic orphan re-check**: 60s interval re-runs `recoverOrphanedRuns()` so mid-session crashes don't strand cards until the next `onOpen`.
- **Orphan recovery** (`recoverOrphanedRuns`): for tasks in `{running, needs_input, needs_approval}` with no live session in `sharedRunRegistry`, reads `runSidecarStore.readHeartbeat(run_id)`. If the sidecar's `at` is within `DEFAULT_STALE_THRESHOLD_MS` (5 min, shared with `RunSession.staleThresholdMs`), the safety net skips adoption; otherwise marks the run failed with an `orphaned by plugin reload` ledger line.
- **Live heartbeat UI**: `useAgentBoardStore.liveHeartbeats: Map<taskId, isoString>` captures the `task:heartbeat` event `at` (set by `useBoardEventRouting`), and `LiveStrip.vue` prefers it over `frontmatter.heartbeat`. Evicted on terminal status (`store.evictLive` on `task:run-finished`). The freshness dot escalates green→amber→red off the store's `nowMs` 1s tick, which is kept off the heartbeat path so a heartbeat stays O(1) per strip.

### Why the split is safe

Status writes (frontmatter) align with turn boundaries where the agent has just paused or ended — it is not mid-`Edit`. The terminal ledger snapshot writes the note in a single `replaceGeneratedRegion` call after the run has settled and the stream is closed. Heartbeat ticks and per-ledger-entry appends — the high-frequency writes that previously raced the agent — never touch the note.

## Work-order chaining

A "workflow work-order" spawns a configured successor when it finishes, so the board runs lightweight pipelines (Design → Implement → Verify) with no new note type or state machine.

- **Config frontmatter** (`model/workOrderChain.ts`, `parseChainConfig`): `chain_template` / `chain_title` / `chain_objective` (any one makes the order a workflow work-order — objective-only is valid) + `chain_trigger` (`done` = spawn after the human accepts, the default; `review` = spawn the instant the agent hands off). **Provenance** frontmatter is separate: `chained_from` (predecessor id), `chained_to` (successor id, the idempotency guard), `chain_depth` (hop count). Templates carry the same `chain_*` keys and a work order inherits them on instantiation (`resolveSeedChain` = `seed.chain ?? template.chain`).
- **`execution/WorkOrderChainCoordinator`** (+ `createWorkOrderChainCoordinator.ts` deps factory, registered from `main.ts` via `app/registerWorkOrderCoordinators.ts` alongside `CommitOnAcceptCoordinator`): one plugin-level subscription to `task:status-changed` — the single chokepoint covering manual runs, queued runs, the accept button, and multiple open board panes. The pure `buildSuccessorPlan` decides skip-vs-create (config present, trigger matches the entered status, not already `chained_to`, depth `< agentBoardMaxChainDepth`, default 25); it loads the predecessor and re-checks the trigger BEFORE reserving the per-path in-flight guard, so a non-matching `review` event can't block the matching `done` event on a back-to-back transition.
- **Successor creation** reuses `createWorkOrderFromSeed` with a `postProcess` hook that seeds `## Context` (`writeChainContext`: a `[[wikilink]]` back to the predecessor + its handoff next-action, blockquoted so an embedded `##` can't split the section) and the objective override (`writeSections`) INSIDE the single `vault.create`, so the note is never `ready`-but-un-seeded for the auto-run queue to race. An agent-only predecessor (roster agent, no explicit provider/model) resolves the agent's backend so the successor stays queue-eligible. Creation retries on a lost filename path race (`commands/workOrderNoteFactory.ts`, `createNoteWithUniqueId`).
- **Durable audit is frontmatter-only**: the coordinator stamps `chained_to` on the predecessor via one atomic `vault.process` (`writeChainLink`) — it never writes the note's Run Ledger region, which a `review`-triggered `writeLedgerSnapshot` replaces wholesale at terminal (a ledger line appended here would be erased). The depth-cap skip surfaces a `Notice` only.
- **UI**: a "Next step" chip in the detail modal's properties panel (`ui/ChainConfigModal.ts` + shared `ui/workOrderChainSummary.ts`, wired at both editable `WorkOrderDetailModal` call sites), a "Default next step" section in the template editor, and a link-glyph indicator on chained cards (`WorkOrderCard.vue`).
- **Re-triggering**: the `chained_to` guard is persistent, so re-running a work order that already spawned a successor does NOT spawn a second one — clear `chained_to` first to chain again.
