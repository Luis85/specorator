# Cursor Provider

Adaptor for Cursor Agent over first-party ACP (`agent acp`), built on the shared `src/providers/acp/` transport plus Cursor's own dialect extensions (`runtime/cursorAcpExtensions.ts`).

## Runtime gotchas

- `usage_update` (the accepted ACP session-usage RFD, agentclientprotocol.com/rfds/session-usage.md) is NOT emitted by `agent acp` as of CLI 2026.07.09, per Cursor staff — usage derives from the model-window fallback instead. Don't go hunting for that frame on the wire.
- `session/list` is absent from Cursor's ACP surface — JSONL hydration from `~/.cursor/chats/<workspace>/<session>/` stays the history source of truth. Re-check before proposing a migration to an ACP-native session list.
- `cursor/task`'s notification-vs-request label is unreliable (real captures show it arriving as a BLOCKING request despite docs elsewhere implying otherwise) — treat the documented response schema as the contract, not the label.
- `cursor/generate_image` carries the same label/schema contradiction as `cursor/task` (docs call it a notification but document a response schema); it is registered defensively as a request handler in `cursorAcpExtensions.ts` even though no real capture has shown it firing yet.
- `cursor/update_todos` has the SAME contradiction and it DOES fire as a blocking request in the wild (real captures 2026-07-12: every `cursor/update_todos` arrived with an `id`, and while it was only a notification handler the client `-32601`'d each one and the todo panel never updated in agent mode). It is now registered as both a request (answered with the documented `{ outcome: { outcome: 'accepted', todos } }`) and a notification, sharing one merge/emit helper. In agent mode todos flow through `update_todos`; in plan mode they arrive as `plan` session-updates (see `CursorChatRuntime.emitPlanTodoUpdate`).
- Cursor reports some file deletions as a permission with `kind: 'edit'` and a `Delete `<path>`` title (real ACP fixture), not `kind: 'delete'`, and carries NO `rawInput` — the path lives only in the title. `resolveCursorAcpRawToolName` detects the delete-shaped title (word-boundary anchored, so `Deleted 3 lines` from an edit doesn't match) and resolves to `delete` before the kind fallback, and `normalizeCursorAcpToolInput` parses the path out of the title and seeds `input.path` (unless a real `rawInput.path` is present) — otherwise the tool normalizes to `Edit` OR resolves to `delete` with an empty path, `collectRemovedPathsFromToolCall()` finds nothing, and the removed file lingers in the edited-files list. The title reaches the mapper via the shared `AcpToolStreamAdapter.normalizeToolInput(rawName, input, title?)` seam.
- Token/cost telemetry: no `usage_update` frame is emitted, so `this.contextUsage` is usually null and the context window comes from the model catalog. `emitFinalUsage` passes the catalog window to `buildAcpUsageInfo` as `fallbackContextWindowSize` so a `session/prompt` response that DID carry token counts keeps the window/percentage (non-authoritative) instead of collapsing to `contextWindow: 0`.
- The blocking extension handlers (`cursor/create_plan`, `cursor/update_todos`, `cursor/ask_question`) all guard on the per-turn cancel signal (`getAskSignal().aborted`) BEFORE emitting: an agent that ignores `session/cancel` can send a late request after Stop, and without the guard it would queue plan text / refresh the todo panel into the already-cancelled turn. The RPC is still acked (`cancelled` for plan/ask, `accepted` with the raw todos for update_todos) so the agent isn't left hanging; only the transcript emit is suppressed.
- ACP diagnostics capture (`captureAcpTraffic`, off by default) reconciles mid-session WITHOUT a respawn: the wire/stderr sink hooks are always wired and read `this.captureWriter` dynamically, and `CursorChatRuntime.reconcileCaptureWriter` (called from `ensureReady`'s reused-process branch) builds the writer when the toggle flips on and flushes+drops it when it flips off. A toggle no longer waits for an unrelated restart to take effect (so turning capture off stops recording prompt-bearing frames immediately).
- The child env is built via `buildFullSubprocessEnvironment` (full `process.env` spread, Claude-parity — the allowlist was removed 2026-07-13). It ships a SINGLE PATH key: Windows env-var names are case-insensitive, so `process.env` carries `Path` while our PATH enhancement writes `PATH`; shipping both let a child shell resolve the un-enhanced `Path`, so case-variant PATH keys are collapsed into one canonical `PATH`.
- Windows shell executor: prefer Git Bash over PowerShell. We spawn `agent acp` with `windowsHide: true` (no console — avoids the terminal flash), but a console-less PowerShell is a broken executor for cursor-agent's shell tool: its child loses System32/Git from PATH (bare `git`/`cmd` "not recognized") AND swallows external-program stdout (`& git.exe` → empty), forcing the agent into absolute-path + file-redirect workarounds (real capture 2026-07-12, `rawOutput.stderr`). cursor-agent doesn't propagate our env to that shell, so fixing our PATH doesn't reach it. `cursorAgentEnv.findWindowsGitBashShell` therefore points `SHELL` at Git Bash (`<ProgramFiles>/Git/bin/bash.exe`, + MSYSTEM/EXEPATH) when Git for Windows is installed: MSYS2 bash resolves `git` from its own runtime and captures child stdout via a pty without a Windows console. PowerShell stays the fallback only when Git Bash is absent.
