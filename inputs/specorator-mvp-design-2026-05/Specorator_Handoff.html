Section 01

Overview

Specorator is an Obsidian plugin that provides a GitHub-integrated workspace for AI-agent-driven development. It replaces context-switching between GitHub, a task manager, and your editor with a single three-panel interface living inside Obsidian.

Goal

The plugin surfaces issues, tasks, agent activity, and pull requests in a single pane. AI agents operate on the codebase and vault, producing proposals for the user to review and accept before any file is committed. The user never leaves Obsidian.

✦
The prototype (Specorator Screen v2.html) is a self-contained reference implementation in vanilla HTML/CSS/JS. All data, state, and render logic is contained in one file and can be read directly as a functional specification.
Three-Panel Layout
Left Sidebar (240px) | Main View (flex: 1) | Right Sidebar (284px)
Actions · Issues · PRs | Issue / PR / Task / Feed | Tasks / Agents / PR Panel

The layout is fixed — all three panels are always visible. Only the content of each panel changes based on what is selected. A status bar sits below all three columns.

Section 02

Data Models

TypeScript interface definitions derived directly from the prototype data structures. These represent the minimum viable shape for the production data layer. Fields marked optional are shown but not required for the initial implementation.

Issue
interface Issue {
  num:         number;              // e.g. 191
  type:        IssueType;           // 'feat' | 'fix' | 'research' | 'chore' | 'docs' | 'req'
  scope:       string;             // e.g. 'plugin-shell', 'ui', 'tooling'
  eyebrow:     string;             // derived: "{scope} · {type}"
  title:       string;
  subtitle?:   string;
  description: string;             // may contain basic HTML (code tags)
  context?:    string;             // acceptance criteria, notes, constraints
  status:      'open' | 'closed';
  opened:      string;             // relative time string
  linkedPRs?:  number[];           // PR numbers (not IDs)
}

type IssueType = 'feat' | 'fix' | 'research' | 'chore' | 'docs' | 'req';
Task
interface Task {
  id:       string;                  // unique, e.g. 't0', 'bd0-1234'
  label:    string;
  est:      string;                  // display string: '2h', '1d', '?'
  status:   TaskStatus;
  agentId:  string | null;           // references Agent.id
  scope:    'issue' | 'backlog';
  issueId?: number;                  // required when scope === 'issue'
}

type TaskStatus = 'todo' | 'in-progress' | 'done';
Agent
interface Agent {
  id:       string;                  // e.g. 'forge', 'scout', 'quill'
  name:     string;
  role:     string;                  // e.g. 'Implementation', 'Dependency Review'
  status:   'Running' | 'Queued';
  code:     'active' | 'queued';    // machine-readable status
  letter:   string;                  // single character for avatar
  grad:     string;                  // CSS gradient for avatar background
  task:     string;                  // current task label
  messages: AgentMessage[];
  live:     boolean;                 // true = show typing indicator
}

interface AgentMessage {
  role: 'sys' | 'agent' | 'tool' | 'user';
  text: string;
  ts:   string;                      // display time, e.g. '14:22'
}
Proposal
interface Proposal {
  id:       string;
  issueId:  number;
  status:   'pending' | 'accepted' | 'rejected';
  type:     string;                  // e.g. 'File Created', 'File Modified'
  path:     string;                  // vault-relative file path
  size:     string;                  // e.g. '21 lines'
  agentId:  string;
  desc:     string;
  code:     CodeToken[];             // tokenised for syntax highlighting
}

interface CodeToken {
  t: 'kw' | 'ty' | 'st' | 'pn' | 'cm' | 'tx' | 'br';
  v: string;
}

// Proposals drive the "Review Required" section.
// status changes from 'pending' → 'accepted' | 'rejected' trigger a re-render.
// Accepted proposals appear in the Related Files section.
Pull Request
interface PullRequest {
  id:           string;              // e.g. 'pr45'
  num:          number;
  title:        string;
  branch:       string;
  base:         string;
  status:       'open' | 'merged';
  draft:        boolean;
  issueIds:     number[];            // linked issue numbers
  author:       string;
  authorGrad:   string;              // CSS gradient for avatar
  authorLetter: string;
  opened:       string;             // relative time string
  checks:       'passing' | 'failing' | 'pending';
  reviewStatus: ReviewStatus;
  additions:    number;
  deletions:    number;
  commits:      number;
  description:  string;
  files:        PRFile[];
  ciChecks:     CICheck[];
  activity:     ActivityEvent[];
}

type  ReviewStatus = 'review-required' | 'approved' | 'draft' | 'merged';

interface PRFile {
  path:  string;
  kind:  'created' | 'modified' | 'deleted';
  adds:  number;
  dels:  number;
}

interface CICheck {
  name:   string;
  status: 'pass' | 'fail' | 'pending';
}
Activity Event
type ActivityEventType =
  | 'opened' | 'commits' | 'ci' | 'comment'
  | 'review' | 'merged' | 'agent' | 'proposal'
  | 'task' | 'closed' | 'pr';

interface ActivityEvent {
  type:     ActivityEventType;
  ts:       string;              // relative time or HH:MM
  author?:  string;
  grad?:    string;              // avatar gradient
  letter?:  string;             // avatar letter
  text?:    string;
  body?:    string;              // for comment/review types
  status?:  string;             // for ci/review types
  note?:    string;
  icon?:    string;
  color?:   string;
  items?:   CommitItem[];       // for 'commits' type
  issueNum?:number;
  prNum?:   number;
  prId?:    string;
}

interface CommitItem {
  sha: string;  // short SHA, 6–7 chars
  msg: string;
  ts:  string;
}

State & Routing

The plugin uses a single flat state object. There is no router — renderMain() and renderRight() are called whenever state changes. Each render reads from state and generates HTML (or React elements in production) for the appropriate view.

App State Object
interface AppState {
  main:     'issue' | 'pr' | 'task' | 'activity';
  right:    'tasks' | 'agents' | 'agent' | 'pr';
  issueId:  number;        // default: 191
  taskId:   string | null;
  agentId:  string | null;
  prId:     string | null;
  prevMain: AppState['main'] | null; // for breadcrumb back navigation

Section 05

Key Interactions

The three most complex interaction flows — proposal review, PR merge workflow, and task assignment. Each involves multi-step state mutation and conditional re-rendering.

Proposal Review Flow
Agent writes file→Proposal created, status='pending'
"Review Required" shown→Amber-tinted card with code preview
User clicks "View diff"→DiffModal opens, built from proposal.code tokens
User clicks "Accept"→proposal.status='accepted', section re-rendersalso triggers re-render of Related Files
User clicks "Reject"→proposal.status='rejected', card removed from view
All proposals reviewed→Section header shows "✓ All reviewed" in green
✓
Accepted proposals should appear in the Related Files section at the bottom of the issue workspace. Filter: PROPOSALS.filter(p => p.issueId === issueId && p.status !== 'rejected')
PR Merge Workflow (Gated)
PR opened (non-draft)→reviewStatus='review-required'
Review & Merge section→Shows Approve + Request Changes. Merge locked.
User clicks "Approve"→reviewStatus='approved', panel re-renders
Merge button appears→Enabled if checks='passing', disabled if not
User clicks "Merge"→800ms delay → status='merged', sidebar pill → purple ✓
Draft PR path→"Mark as Ready" shown instead. Converts draft=false on click.
⊛
Merge gate rule: mergeButton.visible = pr.reviewStatus === 'approved'. This is intentional — the UI should prevent merging unreviewed code regardless of CI status. CI status only affects whether the visible merge button is enabled or disabled.
Task Assignment Flow
Unassigned task card→Shows "Assign →" button
Click "Assign →"→AgentPicker dropdown positioned near button
Select agent→task.agentId=id, task.status='in-progress'
Re-render→Task moves to In Progress section. Right panel task list updates.
Outside click→AgentPicker dismissed. document.addEventListener('click', handler, {once:true})
Section 06

Obsidian Integration Notes

The prototype is a standalone HTML reference — not an Obsidian plugin. These notes bridge the gap between the prototype's static data model and the production plugin architecture.

Plugin Architecture
✦
Recommended stack: React (already used in Obsidian plugin ecosystem) + TypeScript. The three-panel layout maps well to an Obsidian WorkspaceLeaf per panel, or a single leaf rendering all three columns.

Open Items & Known Gaps
⚠
Proposal persistence — Proposals must survive Obsidian restarts. Store as a JSON file in the vault (.specorator/proposals.json) and reload on plugin init. The accept/reject UI is fully designed; only the persistence layer is missing.
⚠
Agent WebSocket — The agent chat log in the prototype is static. In production, each agent's message stream should be a live WebSocket or SSE connection. The typing indicator (live: boolean on Agent) should be driven by connection state.
⚠
Issue filtering — "My Issues" and "Created Issues" currently show toasts. These need to be connected to actual GitHub API filter params: ?assignee=@me and ?creator=@me respectively.
⚠
Activity Feed live updates — The feed is static in the prototype. In production, new events should be appended to the top of "Today" without a full page re-render. Recommend a React state array + append-only updates.
✦
CSS tokens — All colours, fonts, and spacing are defined as CSS custom properties at :root. These should be mapped to Obsidian's theme variables (--color-base-*, --font-text-*) so the plugin respects the user's Obsidian theme automatically.
✓
No build step for the prototype — Specorator Screen v2.html opens directly in any browser. Use it as a living spec — it is the authoritative visual and interaction reference. All data models, state logic, and render functions are fully readable in the source.
